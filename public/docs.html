Documentation

Allowance lets an AI agent earn and spend NEAR, but only inside rules a human wrote. A smart contract enforces the rules, so a fooled agent still can't overspend.

Core concepts

  • Agent: the account your AI controls. It can only call request_payment.
  • Owner: you. You set the rules, approve held payments, pause and resume.
  • Guardian: an optional pause-only account, a circuit breaker. It can never pay, approve or resume.
  • Policy: caps, daily budget, hourly rate, per-recipient caps, allowlist and blocklist.
  • Decision: every request ends as paid, held or blocked, with the reason on record.

How a payment is decided

Checks run in this order and stop at the first failure:

  1. Is the agent paused? If yes, refuse.
  2. Is the recipient on the blocklist? Refuse.
  3. Is the recipient on the allowlist? If not, refuse.
  4. Is the amount over the per-payment cap? Refuse.
  5. Would it exceed today's budget, the hourly rate, or that recipient's daily cap? Refuse.
  6. Is the amount above the approval threshold? Hold it for the owner.
  7. Otherwise pay.

Quickstart

git clone https://github.com/sasindu-smart/allowance
cd allowance
npm start        # http://localhost:3000
npm test         # 90 tests

The default mode needs nothing else. Open /app, click Let the agent act a few times, then Send an attack message.

Owner wallet

In near-contract mode, click Connect wallet in the app and choose a wallet (Meteor, Sender, Nightly, HERE and more). Connect the account that is the contract's owner. Approve, reject, pause and resume are then signed in your wallet, and your keys never reach Allowance.

After you sign, the server checks the transaction on the NEAR RPC: it must be signed by the owner, sent to this contract, call the expected method, succeed, and (for approve and reject) be about the same payment. Only then does the dashboard update. A transaction hash can be used once.

The Live on-chain state card reads get_state directly from the chain, so you can compare the dashboard with the truth.

Security model

  • The rules live in the contract, not in the agent. A jailbreak changes what the agent asks for, not what the contract allows.
  • Power is split across three accounts, so one stolen key can only do limited damage.
  • The pause is stored on-chain, so a modified server cannot skip it.
  • Model output is validated before use, and message-triggered payments are marked untrusted.

Honest limits

Please read. This is hackathon software on testnet. The contract has not been audited and must not hold real funds. Cross-chain payouts are price quotes only. There is no TEE. Wallet connect depends on third-party wallet libraries loaded from a CDN. Dashboard figures are demo accounting scaled by PAYMENT_SCALE, not the contract's raw balance.

FAQ

Does the agent hold my funds?

In contract mode the funds sit in the contract account. The agent's key can only call request_payment.

What if the agent is fully jailbroken?

The rules aren't inside the agent. Use "Attack a compromised agent" in the app to see a model that obeys every instruction still get refused.

Why did I see "Would exceed the daily limit"?

In contract mode the daily counter lives on-chain and resets at UTC midnight. "Reset demo" does not reset it.
